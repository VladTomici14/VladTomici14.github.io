Handover · DokuWiki aichat plugin

Connecting the wiki AI chat to our Qwen and TEI servers

These are the steps to turn on the AI chat in our DokuWiki, using our internal Qwen3.5-9B (vLLM) and TEI embedding servers. Vlad tested the whole setup on a local copy; what's left needs wiki admin and server access.

  • From Vlad
  • Tested 12 Oct 2026
  • About 1 hour of work, plus one decision (step 2)

How it fits together

The aichat plugin splits every wiki page into small pieces, turns each piece into a vector using the embedding server (TEI), and stores them in a small SQLite database inside the wiki. When someone asks a question, the plugin finds the most relevant pieces and sends them, together with the question, to the chat model (Qwen on vLLM), which writes the answer.

vLLM · Qwen3.5-9Banswers questions

Both servers speak the OpenAI API format, so the plugin uses its built-in Generic provider for both.

Before you start

  • Wiki admin account, for Admin → Configuration Settings and the Extension Manager.
  • Shell access to the wiki server, or someone who can run commands there. Indexing only works from the command line; the plugin has no button for it.
  • Plugins installed: aichat and sqlite (aichat needs sqlite to store its index). Both are in the Extension Manager.
  • The wiki server can reach both AI servers. Step 1 checks this.

1Check the AI servers from the wiki server

Run these on the wiki server itself, not on your laptop. Both servers are internal-only, so this proves the wiki can actually reach them.

Qwen (vLLM)

# model name to use in step 3: the "id" value
curl -s VLLM_URL/models

# a real answer, in the same format the plugin sends
curl -s VLLM_URL/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"MODEL_ID","messages":[{"role":"user","content":"Say OK"}],"temperature":0}'

Embeddings (TEI)

# note "model_id" and "max_input_length", both are needed in step 3
curl -s TEI_URL/info

# OpenAI-style embeddings route, which is what the plugin calls
curl -s TEI_URL/v1/embeddings -H 'Content-Type: application/json' \
  -d '{"model":"x","input":["hello wiki"]}'

Write down: the Qwen model id, the TEI model_id and the TEI max_input_length.

If a check fails

A timeout means the wiki server can't reach that host (firewall or proxy). An SSL or certificate error means the server's PHP doesn't trust our internal certificate authority. Both need fixing on the server side before going on.

2Give the plugin one URL for both servers

This is the one thing that needs a decision. The plugin's Generic provider has a single URL setting, generic_apiurl, used for both chat and embeddings. It calls <url>/chat/completions for answers and <url>/embeddings for embeddings. Our two servers live at different addresses, so as things stand the plugin can only reach one of them.

Option A: a combined route recommended

Whoever runs the reverse proxy in front of the AI servers adds one base path that sends /embeddings to TEI and everything else to vLLM. The plugin stays the official, unmodified version, so updates keep working.

Vlad tested exactly this locally with a small nginx container.

Option B: a small plugin change fallback

A roughly 10-line change adds a separate URL setting for embeddings. No infrastructure work is needed, but the wiki then runs a modified plugin, and that change has to be reapplied after every plugin update unless it's accepted upstream.

Not written yet. Vlad can provide it if option A isn't possible.

For option A, the proxy rule looks like this (nginx example):

# new base URL for the wiki, e.g. https://<proxy-host>/wiki-ai/v1
location /wiki-ai/v1/embeddings {
    proxy_pass TEI_URL/v1/embeddings;
}
location /wiki-ai/v1/ {
    proxy_pass VLLM_URL/;
    proxy_read_timeout 300s;    # answers can take a while
}

Once it's in place, rerun the step 1 checks against the new address: …/wiki-ai/v1/models should list Qwen and …/wiki-ai/v1/embeddings should return a vector.

3Configure the plugin

Go to Admin → Configuration Settings and scroll to the aichat section. The model fields show a dropdown of suggestions, but you can type any value. Type the Generic … values exactly.

SettingValueNotes
chatmodelGeneric MODEL_IDQwen id from /models in step 1
rephrasemodelsame as chatmodelRewrites follow-up questions
embedmodelGeneric TEI model_idFrom TEI /info, e.g. Generic BAAI/bge-m3
generic_apiurlthe combined URL from step 2Must end in /v1, no trailing slash
generic_apikeyAPI_KEY or emptySent as a Bearer token
storageSQLiteDefault; no extra server needed
chunkSizeabout 70% of TEI max_input_lengthSee below. 512 → 350; 8192 → keep 1500
skipRegex^sidebar$|:(playground|sandbox)(:|$)Pages not to index. No slashes around it
custompromptour system promptVlad has the text
restrictempty, or e.g. @userLimit who may use the chat
loggingon while testingQuestions and answers, in Admin → Log Viewer
Why chunkSize matters

The plugin splits pages into chunks of chunkSize tokens. TEI rejects any text longer than its model's max_input_length. The plugin can't look that limit up for a Generic model, and it counts tokens a little differently from TEI, so keep a margin. In the local test, the default of 1500 would have failed against a 512-token model; 350 worked.

4Build the index

On the wiki server, from WIKI_DIR, as the web server user (often www-data) so file permissions stay correct:

cd WIKI_DIR
sudo -u www-data php bin/plugin.php aichat embed     # index all pages
sudo -u www-data php bin/plugin.php aichat info      # shows models in use and chunk count

The first run takes a while on a big wiki. Later runs only process pages that changed.

Keep it current. New and edited pages only reach the chat after the next embed run, so schedule it, for example nightly:

# crontab of www-data: every night at 02:00
0 2 * * *  cd WIKI_DIR && php bin/plugin.php aichat embed >/dev/null 2>&1
Full rebuild

After changing embedmodel, chunkSize or skipRegex, rebuild from scratch: php bin/plugin.php aichat embed --clear.

The plugin only sees pages that are in DokuWiki's own search index. If a page never shows up in chat answers, open it once in the browser or run php bin/indexer.php, then embed again.

5Put the chat button on every page

The plugin only shows the chat where its tag is placed. To get a floating chat button on every page, put the tag in the sidebar page, which the default template shows everywhere:

  1. Open doku.php?id=sidebar, then Create this page or Edit.
  2. Add this line (if a sidebar already exists, add it to the existing content):
<aichat button float>Hi! Ask me anything about this wiki.</aichat>

button shows a button that opens the chat, float pins it to the corner of the screen, and the text inside is the greeting. If the button doesn't appear, check the sidebar setting under the main DokuWiki configuration. With a different template, any page that template shows everywhere (a footer page, for example) works the same way.

6Test it

From the command line first, because it shows each stage on its own:

php bin/plugin.php aichat similar "how do I set up the VPN"   # embeddings + search only
php bin/plugin.php aichat ask "How do I set up the VPN?"       # full answer with sources

Then in the browser: open any page, click the chat button and ask about a page you know exists.

  • similar lists the right page with a score around 0.75 or higher
  • ask returns an answer and the source page
  • The chat button appears on every page and answers in the browser
  • The question shows up in Admin → Log Viewer → aichat (if logging is on)

Troubleshooting

The answer says "I could not find this information" but lists the right page as a source
Search worked; the model ignored the context. In the local test this happened because the custom prompt was too strict for a small 3B model, and removing the prompt fixed it. Qwen3.5-9B should cope, but if it happens, simplify customprompt.
Answers contain the model's reasoning or <think> text
Qwen models "think" before answering, and the plugin doesn't strip that text for the Generic provider. The vLLM server should be started with a reasoning parser (for Qwen, --reasoning-parser qwen3; check the model card) so the reasoning is returned separately.
Indexing fails with "input too long" / HTTP 413 or 422
chunkSize is bigger than TEI accepts. Lower it, then run embed --clear.
Indexing or answering fails with a 404
generic_apiurl is wrong. It must be the base ending in /v1: the plugin adds /chat/completions and /embeddings itself.
Timeouts on answers
Raise the proxy read timeout (see step 2). Long questions with lots of context take time on a 9B model.
Need more detail
Add --loglevel debug to any aichat command. php bin/plugin.php aichat page -d <pageid> shows exactly what was indexed for one page.
Tested on a local copy: DokuWiki (linuxserver image), aichat plugin from the official repository, TEI with BAAI/bge-small-en-v1.5, an nginx gateway as in option A, and a small local model standing in for Qwen. Questions → Vlad.
